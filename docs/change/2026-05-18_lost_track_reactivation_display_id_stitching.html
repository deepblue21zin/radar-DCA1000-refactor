lost track reactivation 및 display ID stitching

목적

멀티 타겟에서 한 사람이 잠깐 끊긴 뒤 새 track_id로 다시 태어나면서 표시 궤적이 여러 ID로 분할되거나, 같은 ID의 비연속 구간이 긴 직선으로 이어지는 문제를 줄인다. 내부 tracker ID와 영상/표시용 stable ID를 분리해 디버깅 가능성과 표시 안정성을 함께 확보한다.

변경 내용

  • recent_lost_track_memory_frames로 최근 LOST track을 삭제하지 않고 보관하는 기간을 추가했다.
  • reactivation_gate_m, reactivation_direction_weight, reactivation_doppler_gate_bins를 association 비용에 반영해 새 후보가 잃어버린 track 근처면 기존 ID로 복구되도록 했다.
  • TrackEstimate.display_id를 추가하고, display_id_stitching_enabled가 켜졌을 때 표시용 stable ID를 별도 배정한다.
  • live viewer, raw replay stage cache, serialized trace에 display_id가 남도록 연결했다.
  • Streamlit Stage Debug의 multi-object plot에서 display 단계는 display_id 기준으로 묶고, 프레임 gap 또는 큰 위치 jump가 있으면 같은 ID라도 선을 끊어 표시한다.
  • Stage Cache schema를 12로 올려 기존 cache가 자동 재생성되도록 했다.
  • 기본 튜닝에 lost memory 24프레임, reactivation gate 0.85m, display stitching 36프레임/0.9m를 추가했다.
  • Streamlit 장시간 실행 중 tracking_core.types가 stale 상태로 남아 display_id 필드를 모르는 문제를 막기 위해 Stage Cache reload 범위에 하위 types 모듈을 포함했다.
  • 예전 TrackEstimate 객체가 섞여도 dataclasses.replace 실패 없이 display_id를 붙이는 fallback을 추가했다.
  • Streamlit app rerun 시 stage_cache 모듈도 reload해 Force Generate가 stale 모듈을 덜 물도록 했다.

합성 검증에서는 LOST track 보관/복구가 켜진 경우 새 후보가 기존 track_id=1로 복구되었고, 보관/복구가 꺼진 경우 내부 track_id=2로 새로 태어나되 표시용 display_id=1로 stitch 되었다.

추가 오류 확인 결과, Streamlit에서 발생한 TrackEstimate.__init__() got an unexpected keyword argument 'display_id'는 오래 살아 있던 Python 프로세스가 하위 dataclass 모듈을 reload하지 않아 생긴 stale module 문제였다. reload 범위와 fallback을 보강한 뒤 20260518_205535 stage cache 250프레임 재생성이 성공했고, display_output.confirmed_tracks에 display_id가 저장되는 것을 확인했다.

남은 위험 또는 다음 후보

  • 실제 사람이 교차하거나 매우 가까워지는 구간에서는 display ID stitching gate가 너무 크면 다른 사람에게 ID가 붙을 수 있다. 교차 시에는 doppler gate와 direction weight를 더 보수적으로 조정해야 한다.
  • 현재 표시 plot은 큰 gap/jump를 선으로 잇지 않지만, 영상에서 끊긴 구간을 보간해 자연스럽게 움직이는 기능은 별도 display interpolation 단계로 분리하는 것이 안전하다.
  • reactivation event가 실제 로그에서 얼마나 발생하는지 보려면 교차/가림이 더 강한 멀티 타겟 raw를 추가로 확보해 비교해야 한다.
